# 段階 2: 実装

user の手が必要になるまで実装を続ける
設計段階で user と合意していない実装 (= 機能の追加、削除、その他も含む) を勝手に進めるな。実装中に必要だと思った場合、user に相談しろ
実装中に見つけた問題、相談、動作確認、が発生したら手を止めて user に相談しろ

## コメント

- WHY が非自明な不変則・制約・workaround のみ残す。WHAT は書かない (= well-named identifier で十分)
- 外部資料参照 (design.md, branch artifact, 段階番号, 「詳細: ...」系) を書かない。ただし knowledge への参照は OK
- 歴史的経緯 (= 「以前は〜」「〇〇だったが ZZ に変更」「Week N」「段階 N」「R-3 確定」など) を書かない
- 思考途中 / TODO / FIXME を書かない
- caller やフローの言及 (「X で使われる」「Y フロー由来」) を書かない (= PR 説明や git blame の話)

### 後でやる印 (= LATER)

code 内 deferral は **LATER 1 種類のみ** allow。「今やる」系 (=TODO / FIXME) は全部禁止 (=urgency があるなら今実装する)

- **LATER**: いつかやるためのメモ (= urgency なし、trigger 駆動)。design smell / future enhancement の備忘。必ず以下 2 つを書く
  - **WHY**: なぜ気になるか / 直す理由 (= 1 行で具体的に)
  - **TRIGGER**: いつ手をつけるべきか (= 「N plugin 増えたら」「X が拡張されたら」等の条件、漠然とした「あとで」は禁止)
  - 例: `// LATER(roomManager に internal subscribe API 追加時): plugin 用 hook を engine 内部 wiring に流用してる、layer 越境`
- 「LATER: あとで直す」「LATER: 改善余地あり」のような **空 deferral は禁止** (= 情報なし、rot 確定)

## 手を止めるタイミング

以下のいずれかに該当したら user に相談する:
- 設計判断が必要な選択肢が 2 つ以上あり、trade-off がある (= どちらも妥当な解だが構造に影響する)
- 見落としていた前提条件が見つかった (= 議論前提が崩れた)
- 設計で確定した方針通りに実装すると壊れる, 矛盾する (= 設計欠陥)
- 既存 file, knowledge との乖離を発見した (= 現実を update する必要)
- 大量変更 (10+ file) を始める前 (= 計画を 1 度提示)
- 動作確認, build 失敗時に原因が複数想定される (= 切り分け方針を user に確認)

## 手を止めた時の伝え方

user に投げる時:
- **何が起きたか** (= 観察事実) を 1-2 行で説明
- **選択肢** (複数案、trade-off table 付き) を提示
- **私の推奨** を明示 (=「私は X 推奨、理由: ...」)

「単独で進めず user に投げる」ことが重要

## 誤判断の訂正

実装中に「前段で出した推奨が誤りだった」と気付いたら:
- 即座に手を止めろ
- user に「前段で X と推奨したが、実装中に Y を発見した、推奨を Z に変える」と明示する
- 中立性プロトコルに従い、何が変わったか (= 事実誤認, 新根拠, 論理立て直し のどれか) を伝える

## type checker, build, 動作確認

- 各段階の実装後に必ず type check を回す
- 既存 test が source 隣にあれば test も併走させる。既存 test を壊していないかの確認 (= 新機能の動作確認には test 通過は不十分、壊さない側だけ守る)
- type check 通過後、user が動作確認したい段階で手を止める。user に動作確認を依頼する
- commit は LLM 自由判断、人間視点の区切り (= user 動作確認境界, 一貫した変更完了時) で切る。各段階で機械的に切る必要はない

## 実装完了時のセルフレビュー

type check 通過後、user に動作確認を依頼する前に以下を自問する
引っかかったら手を止めて user に相談する

- 並行性: 同時に実行されたら壊れる箇所はないか (= 競合状態)
- 原子性: 失敗時に中途半端な状態が残らないか (= 部分成功で整合性が崩れる)
- 網羅性: 新しい値・状態を追加した場合、他の消費者も更新したか (= switch / 許可リスト / enum の全消費者をトレース)
- 境界: ユーザー/テナント/権限の境界を越えていないか (= 認可チェック、IDOR)
- 信頼境界: 外部入力 (user / API / file) を検証なしで信頼していないか
- シークレット混入: API キー / トークン / 認証情報がコード・ログ・エラーレスポンスに含まれていないか

## test を書く判断

新規 test を書く、既存 test を変更する場面では `.claude/skills/dev/test-strategy.md` を Read する
type 選択 (= specification, property, integration, characterization) と LLM への指示精度で test の価値が大きく変わる
「test = 書き換え負債」体感は characterization 中心の書き方で起きる、specification 寄りに振ることで refactor 安全網として機能する

## user 介在のメリット

設計判断は user 視点が必要な場面が多い (= AI 単独では見落とすことがある、異なる視点による検証が必要)
これは AI 側の独走を制御する。「念のため確認」を躊躇するな
